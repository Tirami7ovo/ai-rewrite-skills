# 依据规格重写

接受任意来源的合格规格；不要求先运行某个蒸馏流程。先核对规格的来源、版本、确认依据、适用范围、外部接口与状态规则、目标约束和可运行的测试入口。区分“确认保留”“确认调整”“尚待确认”；已有明确依据的决定直接沿用，缺失依据的行为不补写成需求。若材料不足以判断一个行为，提出具体问题并记录负责人或待答来源。

默认由新上下文的实现者依据核对后的规格、外部契约和测试实现。需要阅读旧代码来识别隐含行为时，把旧代码审查与实现职责分开，并向实现者交付经核对的行为结论、接口和测试语义。若用户要求实现者参考旧实现，遵循该选择，在交接中如实记录参考了哪些旧材料及隔离程度，不宣称独立重写。

按确认保留的行为实现兼容结果，按新验收标准实现确认调整的行为。遇到规格缺口或尚待确认的规则，只暂停依赖该决定的实现和验收；继续可独立验证的已确认范围。取得确认依据后，更新规格、实现和测试的对应关系。UI、依赖或架构调整以重写范围的实际需要为限。

复用既有测试中的业务断言与边界案例，必要时迁移测试代码。旧预期若与已批准调整冲突，记录冲突依据并按新验收标准调整该项预期；保留仍适用的错误、边界和副作用断言。不得仅为使新实现通过而悄悄放宽预期。分别记录功能到 E2E 的对应、实际覆盖、候选版本的运行结果；旧版本通过或测试映射本身都不是新版本通过的证据。

将工作切成可独立验证的范围；协作时明确接口、文件责任、交付物及集成顺序。用 [交接与验收记录模板](references/handoff.md) 保留规格到实现、测试、证据及未决问题的对应。完成时实际运行适用的本地验证，记录版本、环境、命令或步骤和结果；不能运行的项目说明原因与剩余覆盖。实现完成不代表获得生产发布授权。
