# 重写交接与验收记录

按项目规模裁剪这些表，保持每条决定可追溯。输入可以是 PRD、功能清单、接口约定、状态与恢复规则、用户已确认的决定及现有测试；没有某类材料时注明缺失，不要求来自特定技能。

## 1. 输入与边界

| 项目 | 内容 | 来源、版本或确认依据 |
| --- | --- | --- |
| 目标范围与排除项 |  |  |
| 规格与决定记录 |  |  |
| 外部接口、错误与副作用约定 |  |  |
| 状态、恢复与迁移规则 |  |  |
| 目标环境、依赖与约束 |  |  |
| 现有测试、可运行入口与环境 |  |  |
| 旧实现参考边界 | 实现者是否读取旧代码；审查者的独立职责 | 用户选择或任务约束 |

## 2. 行为和工作切分

| 行为 ID | 状态：确认保留／确认调整／尚待确认 | 旧行为或现有断言 | 目标行为与验收标准 | 证据、批准者或待答问题 | 依赖的实现范围 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

对“确认调整”，写明旧预期与新决定的冲突点，以及哪些原有业务断言仍有效。对“尚待确认”，提出能作出决定的具体问题，标出仅受其影响的工作；不自行选兼容策略，也不自动改写 PRD。已有确认依据无需重复索要确认。

| 工作包 | 已确认输入与交付物 | 接口／文件责任 | 依赖与集成顺序 | 可独立验证的条件 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

多代理时可将旧代码审查、实现与独立复核分开，避免多个执行者同时改同一文件；具体拆分服从项目规模和用户要求。交接实现者时给出已核对的业务规则与测试语义，注明允许参考的旧材料和实际隔离程度。

## 3. 规格—实现—测试对应

| 行为 ID | 实现位置或变更 | 复用／迁移的测试及保留断言 | 功能到 E2E 的对应 | 实际覆盖及缺口 | 候选版本运行证据 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

“对应”只说明计划或已有映射；“实际覆盖”说明测试是否触达该行为；“运行证据”另记候选版本、环境、输入、时间或运行编号、结果。旧版测试报告不能冒充候选版结果。若更新冲突断言，保留原因、批准依据与替代边界案例；对仍有效的错误结果和副作用断言继续验证。

## 4. 收尾

- 已完成的行为 ID 与对应实现、测试证据：
- 实际执行的本地验证（版本／环境／命令或步骤／结果）：
- 未运行或未覆盖的检查、原因及影响：
- 未决问题、受阻范围、负责人或确认渠道：
- 独立复核发现与处理：
- 发布授权状态：实现验收与生产发布分别记录；没有授权时不得写成已获发布批准。
