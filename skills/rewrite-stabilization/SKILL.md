# 重写后的稳定观察与有界修复

接受问题范围或观察目标、候选与旧基线、运行材料及已有约定。先核对版本、环境、时间窗、流量与负载、数据集、样本量、指标定义和业务目标。把可直接比较的结果与条件不同的线索分开；条件不齐时指出缺口，提出同条件采集或隔离复现方案，不宣称已改善性能。错误率、业务失败和副作用可能比单项延迟更紧急，按实际影响确定优先级。

沿用行为依据，将涉及的行为标为“确认保留”“确认调整”“尚待确认”。保留项的偏差按回归核查；获批调整按新目标验证；未决项列出决策问题，不替用户定规则。保留仍适用的既有测试业务断言。功能到 E2E 的对应、实际覆盖、候选版本运行通过须分别记录，旧版结果不能替代新版验证。

定位与观测结果有关的代码路径、请求类别和边界，在用户已授权的范围内做最小且可独立验证的修复或性能调整。保存修复前后的版本、条件、指标与错误样本，复跑相关测试及受影响的端到端路径；性能结论须基于可比条件。若暂无源码、运行环境或可执行授权，交付证据缺口、采集步骤、验证方法及决策点，明确标记未运行。不要把专项稳定工作扩成全系统再次重写。

交付当前问题的处置结果、可比较的指标、测试状态、已知风险和剩余观察项。为观察项写明指标、采集来源、责任或运行机制、触发与退出条件；阈值依据项目目标和风险，不凭空设定。只有实际创建或核实了运行中的调度、监控与告警，才称“持续监控中”；否则写明当前仅有一次分析或监控安排建议。按需使用 [观察与处置记录模板](references/observation-record.md)。
