# 旧系统规格蒸馏

接受提取范围和现有材料，产出有证据支撑的规格包：PRD、功能清单、外部接口约定、状态与恢复规则、功能到 E2E 的对应表。五项可以按项目格式分别保存或组合组织，但都须独立可辨。只对已取得的材料和范围声称完成提取。

全程用一个判据区分需求与机制：**可观察**。用户、上下游系统、运维或现场设备能看到差别的行为是需求；只在系统内部可见的做法是机制，如实记录，重写可以换。下游的重写与审计按"确认保留"实现兼容结果，混进"保留"的机制会被照抄。

需要字段和可直接改用的表格时，读取 [交付物与记录模板](references/deliverables.md)。模板字段是核对要点，可适配项目已有格式，不要求固定文档工具或文件名。

## 步骤

1. **锁定范围与重写目标。** 记录提取对象、边界、材料清单及已知版本。同时写明重写目标：对外兼容面（协议、数据格式、扩展接口、持久化格式）、范围内外的系统、非功能基线的来源。
   - 目标未知时开成首批待确认问题。
   - 不从历史约束、旧路线或模型判断推断目标。

   完成：重写目标每一项都有依据，或有对应的待确认问题。

2. **独立提取。** 对协议/文档、旧代码、测试、运行记录及已认可的新要求，分别提取候选结论。
   - 条件允许时，安排两个独立上下文先各自提取，再由独立审查者对照原始材料核对。
   - 目录里已有其他方（含其他模型）的蒸馏产物时，本方定稿前不读其结论，对照另起一轮。
   - 多方一致不是证据，独立审查也不能替代来源证据。

3. **能力普查。** 按 [入口面清单](references/surfaces.md) 逐类列出系统的对外入口与承载能力的代码，每项归入**交付**、**待定**或**不交付**。
   - 不交付：退役功能、死代码、测试与诊断工具。
   - 待定：契约允许、端到端却不可用的能力。

   完成：清单没有未归类条目，每个交付项都落到功能清单。

4. **判定。** 为结论与证据建立稳定编号，记录每条结论关联的 PRD 需求、功能、接口、状态规则及 E2E 编号，以及来源的已知版本、可定位位置、对本次重写的适用性及其依据。材料不支持的目标、指标、接口语义或运行结果不得补全。
   - 每条行为结论分写**可观察要求**与**现机制**，只有可观察要求能标"确认保留"。
   - 分类为"确认保留""确认调整""尚待确认"。有明确适用于本次重写的用户决定、已认可需求或兼容要求支持时，按其判定，不因旧材料矛盾而重复索要确认。
   - 目标或材料适用性未知时，并列保存文档、实现、测试的证据，标为尚待确认，写明问题与影响范围。不凭文档已签署、版本较新或模型认为更合理来选定目标。
   - 目标明确而现实现偏离的，结论按目标写，偏离另记疑似缺陷；疑似缺陷本身不授权改变兼容行为。

5. **运行取证。** 静态推导出的恢复类、可靠性类结论，列为运行取证场景：目的、操作、预期、恢复步骤、所需授权。
   - 需要写入共享环境的取证，开始前一次性确认授权范围与工具权限，结束后恢复原状。
   - 结论按运行证据更新；没运行的仍标静态推导。

6. **映射五项交付物。** 功能与规则到 E2E 允许多对多，分别标明用例定义、覆盖判断、实际执行结果。
   - 测试中的既有业务断言要留痕；列出用例不等于覆盖或通过。
   - 没有 E2E 时标出缺口和可补场景，不编造用例，也不自动扩大到补建测试。
   - PRD 带上非功能要求和不交付清单。

7. **交接检查。** 运行 `python3 <本技能目录>/scripts/check_refs.py <规格包目录> --repo <代码仓库>…` 并通过。
   - 反查行为结论到 PRD、功能、接口、状态及 E2E 的编号关联。
   - 核对每条确认保留的结论都能写成可观察的验收标准，写不出的部分改归机制或尚待确认。
   - 写明哪些范围可用于实现、哪些仍依赖决定或取证；待确认事项不妨碍已取证范围交付。

8. **盘问待确认事项。** 交付后接着按 [盘问方法](references/grilling.md) 逐轮盘问待确认问题，每轮答复立即写回规格包。

   完成：盘问前沿为空，或用户明确暂停；剩余问题写明负责人。
