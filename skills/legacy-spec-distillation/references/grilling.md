# 盘问方法

规格包交付后，待确认问题不能停在清单上，要通过盘问变成决定。

环境里如果有 `grilling` 或 `grill-with-docs` 技能，可以直接用它；写回规则仍以本文件第 3 节为准。

## 1. 先建依赖树

- 把待确认问题排成依赖树：一个决定会改变哪些问题的答案，它就是这些问题的前提。例如"对外是否保持兼容"决定了大部分接口类问题。
- **前沿**是前提都已定的那批问题，也就是现在就能问、不必猜测其他答案的问题。

## 2. 逐轮盘问

每一轮把整个前沿一次问完，然后等用户答复。格式：

```
❓ **Q-15** - **<问题标题>**：<分歧或缺失是什么、各候选说法的证据编号、影响哪些功能与验收；有选项时逐个列出>

➡️ <推荐答案及理由>

---

❓ **Q-16** - **<问题标题>**：……

➡️ ……
```

- **措辞**：回答"是"就等于接受推荐答案。
- **一问一决**：一个问题只放一个能独立拍板的决定。待确认清单里捆在一起的问题，提问前先拆开。
- **推荐前复核**：推荐"不交付、收回、删除"这类难以反悔的答案前，回到代码与契约复核它依赖的证据。契约和代码里同名的能力，先核对语义是否相同。
- **事实自己查**，不问用户。只有需要用户拍板的事项才交给用户。
- **还在查的事实**算未定前提：依赖它的问题留到后面的轮次，其余照常问。
- **同一轮里有依赖的问题**：如果某个问题的答案取决于本轮另一个问题，把它放到下一轮。

## 3. 每轮答复后写回

用户的答复是"已认可的新要求"，属于目标依据，不是旧系统事实。每轮答复后立即做下面几件事：

- 每条决定记入决策记录并编号（如 DEC-01），作为改写结论的证据来源。
- 关闭对应的待确认问题：问题行写成"已决 <决定编号>（日期）：…"。
- 改相关行为结论的分类（确认保留 / 确认调整），证据栏引用这条决定。确认调整要写明旧行为、新目标与新验收标准。
- 同步受影响的 PRD 条目、功能清单的交付状态、接口约定、状态规则与 E2E 对应。
- 答复里出现新术语或改了术语含义时，同步统一语言或术语表。
- 引用该问题的每一行，按决定改写成目标，或在同一行注明"已决"与决定编号。运行 `check_refs.py` 直到通过（无法运行时人工核对），它会拦下仍按未决引用的行。不带问题编号的旧结论，按决定的关键词再搜一遍。
- 重新计算前沿，再问下一轮。

## 4. 结束

- **结束条件**：前沿为空，或用户明确暂停。暂停时，剩余问题写明负责人和需要补的证据。
- **收尾**：回到 SKILL 第 7 步重跑交接检查，重写"可直接实现 / 剩余事项"两部分，剩余事项每条写明负责人。
- 盘问期间只改规格包，不据答复动代码或启动实施。
