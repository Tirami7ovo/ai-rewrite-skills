# 方法来源与适配

本技能集受[卡兹克分享的 AIHOT 重写流程](https://x.com/Khazix0918/status/2104555128691073505)启发，并参考[宝玉关于重写验证和 E2E 的补充](https://x.com/dotey/status/2104594943054340098)。以下为原创整理与通用化适配，并非原帖逐字转载，也不代表原作者对本技能集的认可。

## 从原十二步到五个技能

| 原步骤 | 原经验的要点 | 技能中的对应方式 |
| --- | --- | --- |
| 1 | 两个模型独立蒸馏旧项目，保留功能与历史细节 | `legacy-spec-distillation`：独立取证与提取，形成可追溯规格 |
| 2 | 第三个模型对照文档、交接包与旧代码，补充遗漏 | 同一技能中的交叉核对；冲突和证据缺口显式保留 |
| 3 | 实现者不看旧代码，依据核对后的资料和验证依据重写 | `spec-driven-rewrite`：新上下文实现，阅读旧代码的审查职责分离 |
| 4 | 多路对照新旧项目，审查功能与体验差异 | `rewrite-parity-audit`：依据行为、契约和已批准变化审计 |
| 5 | 修复后清空上下文，按模块重新检查遗漏 | 实施者修复，独立新上下文复审受影响范围与关联路径 |
| 6 | 再检查 BUG 与漏洞并修复 | 审计中单独给出缺陷/安全结论，与行为一致性分开 |
| 7 | 统一组件、优化或重设计部分 UI | 仅当项目需求和本次范围包含这些工作时，纳入重写或稳定阶段 |
| 8 | 导出数据、服务器彩排、六小时影子运行并观察问题 | `rewrite-release-validation`：按需迁移、彩排、差分或影子验证 |
| 9 | 全面的端到端测试 | 复用已有 E2E，核对真实覆盖与候选版本执行证据 |
| 10 | 切换上线 | 在授权和验证条件满足时按适用方案切换，并明确回退能力 |
| 11 | 根据真实数据优化缓存、分发、页面等性能 | `rewrite-stabilization`：从实际指标识别瓶颈，验证调整收益 |
| 12 | 监控问题并持续优化 | 有边界的观察与回归处理；明确持续机制是否实际建立 |

## 保留的原则

1. **理解与实现分离。** 先弄清要保留或改变的行为，再让实现者选择适当实现；审查者仍可回到旧代码、协议、测试和运行证据核对。
2. **独立结果再交叉核对。** 可用时安排独立上下文提取和审查；同一个模型的不同上下文也能承担职责，但须如实说明复核的独立性和限制。
3. **修复后重新审查。** 之前通过的结论依赖对应版本；新变更影响哪些规则，就重新验证哪些范围及关联路径。
4. **写完、验收通过和运行稳定分别证明。** 代码生成完成、若干测试通过和短期运行没有报错，各自只支持有限结论。

## 通用化时作出的调整

- **不固定模型、数量或厂商。** 工具和预算允许时并行独立工作；不可用时按可实现方式顺序完成并记录限制。
- **不以逐行相同为目标。** 逐行阅读可以帮助取证，功能等价需要比较输入输出、状态、副作用及适用的时序等约束。
- **不固定六小时。** 观察周期应覆盖实际行为周期和代表性条件；运行时长不替代覆盖和结果对账。
- **不强制 UI 重设计或数据迁移。** 只在项目确有相关对象和变化时执行；不适用时说明原因。
- **不自动扔掉旧单元测试。** 与内部实现耦合的代码可能需要改写；业务断言、边界案例和历史回归知识仍应保留。E2E 也只证明其实际覆盖且执行过的场景。
- **不把模型一致意见当独立事实。** 结论需要定位到证据；同一份遗漏的规格可能同时影响实现与测试。
- **不把缺陷发现等同于变更批准。** 目标行为仍需已认可的依据；确认调整单列新标准，尚待确认不偷偷变成需求。

## 蒸馏产物的增强

蒸馏阶段明确形成五项逻辑交付物：PRD、功能清单、外部接口约定、状态与恢复规则、功能到 E2E 的对应表。它们共享证据编号与三类行为标记，避免产品描述、技术契约和测试清单彼此脱节。

每条结论注明来自哪份协议、哪个代码版本、哪个测试或哪段运行记录；用户明确的目标决定同样可作为需求来源，但应与旧系统事实区分。材料不足写明待确认，不能将看起来合理的推测补成已确定需求。

这些增强是本技能集的设计选择，原案例没有提供所有这些格式或验收标准。原帖属于作者经验自述，不能据此推断任意项目的重写成功率、成本或长期可靠性。
