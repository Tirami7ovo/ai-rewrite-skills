# AI Rewrite Skills：通用重写方法论技能集设计

日期：2026-09-30  
状态：设计已确认；五个技能已实现，通过结构校验、合成场景试用与独立审查。详见[验证记录](validation.md)。

## 目标与已确认边界

将卡兹克的 AI 协同重写经验提炼为多个可以独立安装、独立触发、组合使用的 skills。用户已明确选择多个独立技能，而非一个总控技能。产物是一套通用方法论，不绑定某个项目、行业、系统架构、操作系统、语言、模型厂商或测试框架。

用户的具体项目不进入技能正文、默认模板或仓库示例。现有规格、代码、测试、审计报告均可作为输入，不要求先执行本技能集中的其他技能。

成功标准：另一个 AI 只安装其中一个技能，也能判断输入是否充分，完成对应工作，交付有证据的结果，并说明未验证范围。

## 组织方式

采用五个独立技能，以各自交付的结果划分职责。仓库 README 提供选用说明和可选组合顺序，不作为必须执行的总控入口。

| 技能名 | 触发场景 | 最小输入 | 核心交付物 |
| --- | --- | --- | --- |
| `legacy-spec-distillation` | 从已有系统提取可用于迁移、重写的功能和行为规格 | 协议、旧系统代码、运行记录、文档或测试中至少一种可用证据，以及提取范围 | PRD、功能清单、外部接口约定、状态与恢复规则、功能到 E2E 对应表，以及证据与待确认事项 |
| `spec-driven-rewrite` | 按已确定的规格重新实现系统或指定范围 | 可操作的规格、目标约束、验收依据、可修改范围 | 新实现、规格到实现的对应关系、验证结果、未解决事项 |
| `rewrite-parity-audit` | 检查新旧版本差异，以及重写结果的缺陷和安全问题 | 新版本及预期行为依据；进行新旧对比时还需旧版本证据 | 行为差异报告、独立的缺陷/安全报告、修复建议和复审结论 |
| `rewrite-release-validation` | 评估重写版本是否满足交付和切换条件 | 候选版本、目标环境约束、验收标准和已有测试入口 | 验证证据、适用的彩排结果、发布判断、切换与回退方案 |
| `rewrite-stabilization` | 在重写上线后处理回归、性能和实际运行问题 | 新版本运行信息、已知问题或观测目标，以及可用基线 | 问题与证据记录、针对性修复及回归结果、性能比较、观察结论 |

输入不足时，先完成不依赖缺失信息的工作；仅针对影响当前判断的关键缺口提问。不能把缺失数据补写成已知事实，也不强迫用户把现有材料改成固定文件格式。

## 五个技能的具体设计

### 1. legacy-spec-distillation

先记录本次提取的范围和材料版本，尽可能安排两个独立上下文分别提取，再由独立审查者对照原始材料交叉核对。先独立形成结果，再互相比较，减少早期结论影响后续提取。

#### 五项明确交付物

| 交付物 | 必须表达的内容 |
| --- | --- |
| PRD | 有证据支持的目标、范围、使用场景、需求和验收标准；关联下列清单与规则，并独立列出待确认事项。材料没有给出的产品目标、用户需求或指标不得自动补全。 |
| 功能清单 | 功能编号、可观察行为、适用条件、验收标准及关联规则。正常路径、异常路径及边界条件按证据记录。 |
| 外部接口约定 | 外部交互的输入输出、错误语义及适用的兼容、时序、幂等或副作用约束；依据实际材料提取，不预设协议、接口形态或内部实现。 |
| 状态与恢复规则 | 可观察状态、转换条件、失败或中断后的恢复行为，以及适用的数据保留、重试和重复操作语义；未知项明确标出。 |
| 功能到 E2E 的对应表 | 功能/规则编号、对应场景和断言、用例定位与版本、覆盖缺口，以及可用的实际执行结果和证据。允许多对多关系，不把列出用例等同于已覆盖或已通过。 |

五项是逻辑交付物，可按项目已有格式分别保存或组合组织，不要求固定文档工具。证据清单、行为决策与待确认清单贯穿五项，组成可交接、可核对的规格包。PRD 是这些已取证信息的产品层整理，不是另起一份推测性需求。

#### 每条结论可追溯

所有交付物中的每条结论均关联稳定编号及可定位的来源。证据记录保留已知版本信息；材料未提供版本时如实说明，不伪造版本、行号或运行编号。例如：

- 协议或文档：名称、版本/日期、章节或条款。
- 旧代码：仓库、提交或发布版本、文件与函数/符号等定位信息。
- 测试：代码版本、用例编号/位置及预期断言。声称测试通过时，还需对应版本、环境、运行结果等执行证据；测试定义本身不证明通过。
- 运行记录：系统构建/版本、适用环境、记录时间和可定位的日志、事件或观测结果。
- 已确认的新要求或调整：用户决定或已经认可的需求材料及其定位，明确这是目标要求而非旧系统事实。

证据不足的结论明确标为“待确认”，写出缺什么证据和影响范围。不得用常识、模型置信度或多个模型意见一致代替来源；实现、文档与测试发生冲突时并列记录证据，不默默选择一个版本作为事实。

#### 区分三种行为

| 行为类别 | 含义 | 后续处理 |
| --- | --- | --- |
| 确认保留 | 重写必须满足的业务规则和兼容要求，已有明确依据支持其保留 | 保留验收语义，并关联相应验证；不要求保留内部实现方式。 |
| 确认调整 | 已确定要修正的缺陷或明确要改变的行为 | 单独记录旧行为、调整依据、目标行为和新验收标准；新旧结果不同不自动算回归。 |
| 尚待确认 | 实现、文档与测试相互矛盾，历史逻辑无法解释，或证据不足以确定目标行为 | 保留冲突与缺口，记录需要确认的问题；不得自动升级为保留或调整。 |

确认依据来自用户的明确决定或已经认可的需求、兼容要求等权威材料，不要求对已有明确依据重复确认。发现疑似或已知缺陷，不自动代表已获准改变兼容行为；修正方向或新验收标准未明确时，相关行为仍列为“尚待确认”。

每条行为记录至少包含：编号、结论、所属交付物/功能、三类行为标记、来源及版本、确认依据、验收标准、关联 E2E 与覆盖情况，以及适用的冲突/待确认问题。共享事实由同一编号引用，避免 PRD、接口约定和测试表各自维护不一致的结论。

#### 完成条件

五项交付物齐备，已发现的每条结论可追溯或显式标为待确认，三类行为和证据冲突可见，功能到 E2E 的已知对应与覆盖缺口已列明。没有现成 E2E 时应标注缺口，可提出待补场景；不能编造用例或执行结果，也不自动把补建测试纳入本次蒸馏范围。

允许交付包含待确认事项的规格包，但必须说明哪些范围已可用于实现、哪些仍依赖决定或取证。完成蒸馏不等于所有需求已确认；证据范围有限时，只声明完成该范围的提取。

### 2. spec-driven-rewrite

接受任意来源的合格规格，不依赖第一个技能。默认由新上下文的实现者依据核对后的规格、外部契约和测试实现；阅读旧代码的审查职责与实现职责分开。用户要求参考旧实现时遵循用户选择，并如实记录隔离程度。

实现“确认保留”的行为，并按新验收标准实现“确认调整”的行为。规格来自其他来源时，沿用其已有确认依据与差异记录，不要求先运行蒸馏技能。

发现规格缺口或“尚待确认”行为后，提出具体问题，不以猜测决定兼容行为或自动改写 PRD。只暂停依赖该决定的实现与验收，继续不受影响的已确认范围；取得确认依据后再同步规格、实现和测试。按可以独立验证的范围拆分任务；多代理协作时明确接口、文件责任和集成顺序。

复用现有测试的业务断言和边界案例，按需要适配测试代码。禁止仅为让新实现通过而悄悄放宽预期结果。UI、依赖或架构调整只在重写范围需要时进行。

完成条件：实现范围有可追踪对应关系，适用的本地验证已实际执行，未覆盖部分有明确说明。完成实现不等于获得生产发布授权。

### 3. rewrite-parity-audit

将两类审查分开记录：

- 行为一致性：对“确认保留”检查行为与兼容要求；对“确认调整”检查新验收标准，不机械要求新旧相同；“尚待确认”保持未决，不判为等价通过或擅自作为修复目标。
- 缺陷与安全：新版本是否存在正确性、错误处理、安全或数据完整性问题。与旧版一致不能证明安全或正确。

按风险和范围安排独立审查，使用规格、旧代码、已有测试和实际运行结果等可用证据。逐行阅读只是取证手段，不把不同实现的逐行匹配当成目标。

报告区分已复现问题、有证据的静态发现和待验证推测。审计任务默认输出发现；有修复授权时，由实施者修复，再让新上下文复核受影响范围及关联路径，保持审查结论独立。

完成条件：发现可定位、可说明影响，有验证方式或验证限制；修复后复审有依据；不能根据“多模型都同意”单独作出通过结论。

### 4. rewrite-release-validation

优先盘点和运行已有验收手段，包括端到端测试、接口契约、业务规则测试、数据对账及其他适用检查。区分候选版本缺陷、测试本身不稳定和环境问题，不用反复重试后的偶然通过替代判断。

按实际变化选择增量验证：新旧差分、迁移彩排、代表性负载、影子验证、分批切换等。数据迁移和影子运行不是每个项目的必做项；适用时核对增量变化、状态、副作用、写入隔离和回退可行性。

先按已知要求明确验收、停止和回退条件，必要时只请求缺少的业务决策。是否执行生产切换取决于本次任务的授权；既有授权可继续使用，技能本身不授予额外权限。

完成条件：交付“满足条件／不满足条件／证据不足”的发布判断及依据。根据功能到 E2E 的对应表核对实际执行证据和覆盖缺口；关键验收仍依赖“尚待确认”行为时，不得声明相关范围满足发布条件。观察时长由行为周期和覆盖需求决定，不固定为原案例的六小时。

### 5. rewrite-stabilization

依据真实问题、运行数据和约定目标，比较新旧基线，优先处理回归和实际瓶颈。没有实际观测材料时，产出采集与验证方案，不声称已经改善性能。

对修复和性能调整保存前后证据，并复跑相关测试。优化范围来自观测结果与用户目标，避免无限扩展为再次重写。

完成条件：当前问题范围有处置结果，指标可比较，已知风险和剩余观察项明确。持续监控需要已有运行机制或明确调度安排，不以一句“会继续监控”代替执行。

## 通用运行约定

- 模型以提取者、实现者、审查者、验证者等职责描述；不要求特定厂商、版本、固定模型数量或价格档位。
- 有并行能力时用于真正独立的工作；资源不足时可顺序执行并重新建立审查上下文，如实说明独立性降低。
- 以行为、状态和副作用等可验证结果为依据，不要求保留旧代码组织方式。
- 每个技能自行提供必需模板；不引用其他技能目录内的文件作为运行前提。
- 不适用的检查允许跳过并说明原因；不能把未执行写成通过。
- 每次结果记录当前版本和验证范围。新变更使相关证据失效时，重新验证受影响部分。
- 结论使用稳定编号关联证据及版本，三类行为标记随交接保留。新的确认决定需同步到相关 PRD、功能、接口、状态规则、E2E 对应与验收依据，避免只修改其中一处。
- 沿用用户明确选择与已有授权，只在缺少必要信息、范围发生实质变化或即将执行尚未授权的动作时提问。

## 验证设计

对五个技能逐项检查格式、引用、单独安装后的自包含性和触发边界。再用独立代理进行行为试用，重点检查：

1. 规格蒸馏能否交付 PRD、功能清单、外部接口约定、状态与恢复规则、功能到 E2E 对应表；逐条保留证据与版本，正确区分确认保留、确认调整和尚待确认，不把推测补成需求。
2. 重写能否接受外部规格和现有测试，按保留要求与调整后的标准实现，并把缺口限制在受影响范围，不自行改变验收含义。
3. 审计能否把行为一致性与正确性/安全性分开，将已确认调整与非预期回归区分，并保持未决项可见。
4. 发布验证能否区分 E2E 映射、实际覆盖与执行通过，发现状态或副作用问题，区分执行权限与发布判断，不把固定运行时长当成充分证据。
5. 稳定阶段能否依据真实基线验证改善，而非给出无边界的优化清单。

测试使用虚构的中性项目材料与隔离工作区，不接触用户生产系统。检验实际输出和决策，不只检查关键词；未实际完成的验证如实报告。
